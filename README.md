# Монитор разгона и разворота фьючерсов BingX

Новая версия читает публичные данные BingX без аккаунта и торговых ключей. На каждом запуске она получает **все** USDT-тикеры, затем 5-минутные свечи **каждого** контракта с суточным диапазоном от 8%; VELVET и BAT проверяются отдельно даже в спокойный день. После накопления снимков цен к проверке добавляются быстрые изменения от 1,2% между замерами и более плавный рост примерно от 1,8% за 15 минут или 2,8% за час, даже если суточный диапазон меньше 8%. Жёсткого лимита в 20 монет больше нет.

Рабочие уведомления теперь **только 🔴 SHORT**. Все USDT-контракты BingX остаются в обзоре; жёсткого лимита количества монет нет. Из них сообщение приходит только при сочетании: старый максимум не менее 3× текущей цены, локальный памп от 40% за окно до 12 часов, закрытая 5‑минутная свеча подтверждает разворот при откате не более 12% от пика, расчётный путь к уровню около основания пампа от 20%, отношение пути к стопу от 2,5:1 и риск цены до стопа не выше 12%. Основание оценивается по устойчивым трём закрытиям перед пиком, а главная цель — 90% пути от пика обратно к основанию. Стоп для сценария ставится за максимумом пампа. Это фильтры гипотезы, а не гарантия падения или дневная квота сигналов. Лонг-логика сохранена в исследовательском коде, но в рабочих запусках не рассчитывается и не отправляется.

Перед отправкой сканер повторно получает цену и стакан, проверяет их свежесть, спред, доступную ликвидность для условного объёма 1 000 USDT, дистанцию до стопа и до дальней цели. В Telegram поступают только свежие условия входа: пик, основание, главный TP почти у основания и уровень отмены. Наблюдения и короткие TP от размера стопа не рассылаются. Вход, стоп и цель — расчётные уровни для самостоятельного решения, не ордер или обещание результата. Подробный аудит: [STRATEGY_AUDIT.md](STRATEGY_AUDIT.md).

Проверить локально без отправки сообщений:

```powershell
python -X utf8 run_monitor.py --dry-run
python -m unittest test_monitor.py
python -X utf8 backtest_monitor.py --symbols VELVET-USDT BAT-USDT
python -X utf8 performance_report.py
```

### Тихая проверка отработки сигналов

После каждого **фактически отправленного** нового шорт-алерта сканер сохраняет цену входа, одну главную цель у основания, стоп, признаки рынка и версию кода в ветке `scanner-state`. Следующие 72 часа оцениваются по закрытым 5‑минутным свечам, начиная с первой полной свечи **после** отправки. Успех сценария означает касание дальней цели до стопа, а не небольшой откат. Журнал различает касание цели первым, стоп первым, неоднозначное касание в одной свече, отсутствие касания и пробел данных. Ранее отправленные short/long случаи продолжают проверяться по прежним целям 1R/1,5R/2R за 24 часа. В трёхдневной сводке новые и старые правила показаны отдельно; индивидуальные исходы не рассылаются. После каждых 100 завершённых случаев сохраняется подробная сводка. `performance_report.py` читает её из публичной ветки.

Это проверка **гипотетического сценария сигнала**, не реальных сделок пользователя: сканер не знает, вошёл ли он, по какой цене исполнился ордер и как вышел. История основана на ценах сделок в 5‑минутных свечах, без комиссий, funding и проскальзывания; первые минуты до полной свечи не оцениваются. Повторяющиеся признаки попадают в сводку как гипотезы только при одинаковом направлении разницы в двух последовательных выборках одной версии кода, минимум по 12 случаев в группе и сравнении в каждой. Это не доказывает причинность или прибыльность. Облачный скрипт сам не переписывает правила по такой статистике; изменения требуют проверки издержек и новых случаев. Ветка `scanner-state` находится в выбранном публичном репозитории: журнал символов и расчётных уровней также будет публичным; секреты Telegram туда не записываются.

Код работает в **отдельном публичном** репозитории GitHub, выбранном пользователем; старый закрытый репозиторий не меняется. `.github/workflows/five-minute.yml` поддерживает запуск вручную и редкий резервный `schedule` каждые полчаса. После загрузки GitHub не создавал запланированные runs, поэтому основное расписание настроено в бесплатном cron-job.org: каждые пять минут он отправляет `workflow_dispatch` в GitHub API. Для него используется fine-grained token с доступом только к этому репозиторию и правом Actions: write; токен хранится в настройках cron-job.org и требует замены до истечения срока действия. Нужны разрешённые Actions и секреты `TELEGRAM_BOT_TOKEN` и `TELEGRAM_CHAT_ID`. Токен бота никогда не помещай в код. Workflow создаёт ветку `scanner-state` с несекретными снимками цен и открытого интереса, историей и отметками отправленных сигналов; ему нужен `contents: write`. Расписание проверяй по истории cron-job.org и событию `workflow_dispatch` в **Actions**, доставку — в Telegram. Несколько последовательных автоматических запусков и доставка Telegram уже подтверждены; дальнейшие интервалы зависят от cron-job.org, очереди Actions и ответа BingX.

GitHub [допускает 5-минутное расписание](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows#schedule), но не гарантирует точное время и может пропустить запуск. Для VELVET и других монет обнаружение разворота остаётся статистической гипотезой: предварительный исторический тест не подтвердил стабильного падения на 20–30% после сигнала. Сканер не торгует.

Старая версия Google Apps Script остаётся в прежнем закрытом проекте. Триггеры `runBatWatch` и `runScanner` удалены по поручению пользователя; в Google Apps Script подтверждено «0 triggers». Код старого проекта сохранён. Новый публичный репозиторий содержит только код нового монитора без токена бота.
